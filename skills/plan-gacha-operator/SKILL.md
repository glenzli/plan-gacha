# Travel operator

Use this skill when the user wants their journey imported, adjusted, evaluated or recorded with plan-gacha. The portable package contains `tripctl.mjs`, `tripctl-lib.mjs`, `ITINERARY.md`, the schemas and an anonymous fixture. Node >=22.13 needs no install or network. Read OPERATOR-FLOW.md and ITINERARY.md once for the operation contracts. Use `schema` and `schema --operation TYPE` to discover actual inputs; do not invent tool names. `--input -` accepts structured JSON on stdin. Use the CLI/library for deterministic rules; use AI for interpreting intent, research and explaining tradeoffs. Do not ask Codex to edit source for ordinary travel updates.

## Tools / skill / data

- Tool: the shared deterministic engine, strict schemas, preview token, local store and read-only report. The original four stateless MCP snapshot tools remain a separately verified interface. Rich itinerary operations currently use CLI/library, not an invented MCP endpoint.
- Skill: this operator workflow, uncertainty judgment, source verification and clear user explanation. It must not turn a user rumor or model guess into a provider fact or a completed activity.
- Data: one user-private authoritative journey with revision/history, baseline/current/actual, preferences, constraints, commitments, evidence, alternatives and deadlines. Keep real hotel/whereabouts/order details private and outside Git, source fixtures, public reports and shared code ZIPs. Synthetic fixtures belong in code.

## Every planning turn

1. Resolve the same authoritative journey identity. Read its latest native Library version and full current contents before using a cloud copy. Do not mix chunks from different versions. On a persistent local host, use `read --store journey.json` and `verify`. Record revision and canonical hash. `context --as-of ISO --date YYYY-MM-DD` gives a compact current view without full history snapshots. Read omitted baseline/current/history when needed, and inspect candidate truncation. Never blindly overwrite an older copy.
2. Separate intent from reported facts, live provider observations and assumptions. Extract explicit time zone, dates, stable activity IDs, reservations/fixed commitments, actual progress and uncertainty. Ask only when missing information blocks a concrete safe change; otherwise make a reversible preview with unknown fields. Preserve unfinished checklist items and other alternatives.
3. For a pre-v5 journey, the file/history can be opened unchanged. Adding an itinerary is optional, not an automatic migration. New plans require new explicit IDs. To attach to existing active plans, use `import_itinerary.adoptExistingPlanIds` and preserve the ordered stable stop IDs, title/start/location and all existing projected fields exactly. Missing IDs or mismatches fail; prepare an explicit reviewed conversion separately. Never work around booked/locked guards by replacing the whole file, deleting history or weakening a booking. Baseline import is once only.
4. Obtain evidence through authorized provider tools or public UI research. Keep source URL/reference, observation time, forecast/travel date, units/mode, identity ambiguity and caller-selected expiry. Core has no implicit network or key access. Google/AMap POI ambiguity, disabled traffic, old weather, unconfirmed tickets and unknown cancellation costs remain unknown. Never convert fixture results or an expired estimate into a real feasibility claim. A user deadline is not verified sunset. Qualitative preferences stay qualitative unless the user supplies a numeric limit.
5. Evaluate with `itinerary --input {asOf,dateId?}` (and original `check`, `rank`, `routes` where applicable). Use an actual explicit analysis timestamp. Route/weather/place observations must bind the current activity token and relevant date. The latest failure/stale result wins; no optimistic fallback. `not_proven` is the expected feasibility ceiling, even when estimates fit.
6. Build the smallest explicit operation. Current reported closures/reopenings use `set_plan_dates` with the real evidence time: old or equal-time overlapping reports are refused. Keep user reports as user evidence. Predictions, unknowns and tentative tours stay facts/issues/options; reopening one date does not imply an exhaustive whitelist. Never pass an empty whitelist. Recording a closure leaves schedule/booking/actual records intact and exposes the unresolved conflict. Candidate `canAssign` is ranking eligibility; check `context` application guards and the final preview before claiming it is actionable. `edit_itinerary` supports add/delete/time/location/move/reorder/new day. Actual reports use `record_actual`, separate from plans. Conditional proposals use options and decision points. Resolve their explicit stable plan/date associations from the saved data and source intent; use `set_option_requirements` for old prose or `itinerary_option.record.requirements` for a new branch. Preserve the original text/source. Never guess a location ID or promote legacy/unbound prose to a viable plan: inspect `options`, `unassessedOptions` and `inactiveOptions` consistently through check/context/itinerary. Keep old date-only exclusions when adding a separate later-date candidate for the same place. A held ticket does not prove opening. If a selected branch becomes inactive, review `choice_invalidated` and its retained `previousChoice`; do not keep recommending it. Do authorized lookups and reconciliation on the user's behalf; ask only for a real unresolved preference or ambiguous identity. For conditions, AI/user chooses based on conditions; `choose_option` only records intent. It does not activate a branch or execute cancellation. When the user explicitly confirms an administrative matter is handled, use `set_decision_status` with `completed`, `confirmation:"explicit"`, real source/time and a reason; use `withdrawn` for no longer needed and `open` for explicit reopening. Unknown reports stay uncertain facts/issues, never completion. New status/choice evidence must be newer; do not change timestamps merely to bypass a stale-evidence refusal. Completed/withdrawn matters have no advisory and their exclusively linked options are inactive. Reopening invalidates older choices and restores applicable deadline prompts. Consume `requiresAction`/`advisoryEvents` rather than treating historical text as pending work. Matter completion does not update orders, certify refunds, release commitments or mark a visit done. Do not infer exact departure/arrival/completion/check-in from “after nine”, congestion or ticket status. Preserve tentative reservations as unresolved rather than silently delete them.
7. `preview --revision N` is read-only. Review all before/after changes, protected commitments, strict time conflicts, overlap, unknown/stale evidence and weather risk. A refusal produces zero writes. Do not bypass a refusal through another endpoint. Show a concise plan or generate `itinerary-report` for human read-only Markdown/HTML; request confirmation only when the user has not authorized the specific write or unresolved information prevents it.
8. Use the exact returned operation/revision/previewToken in a mutation with stable idempotencyKey, actor, real reason and explicit at. Local `apply` is locked CAS/fsynced persistence. In ephemeral cloud use `stage --output candidate.json`; its `saved:false` is intentional. The parent then replaces **the same** Library file with retained expected_current_version. Only native successful outer CAS means externally saved. If version conflicts, re-read/re-evaluate/re-preview; never unguarded retry. If response is unknown, inspect history/idempotency before another write.
9. Reopen and verify the resulting revision/hash. Report what changed, useful constraints/unknowns and the concrete persistence receipt. Explain options without overstating certainty. Undo only the latest commit through ordinary preview/apply, creating a new revision. Keep checkpoints. Prototype limits are 200 commits/16 MiB; hitting a limit must preserve state rather than auto-truncate it.

## Reminders and privacy

A decision deadline produces an advisory, not an automation. Completed/withdrawn matters must not generate follow-up prompts; independently authorized parent reminders should consult the current lifecycle. The core does not stop or create those reminders automatically. Existing parent reminders are independent. Do not create duplicate tasks, poll providers, message third parties, place orders, cancel hotels or modify credentials without an explicit authorized request. A user's “decide by 18:00” does not establish free cancellation or order terms. This tool never writes the parent's authoritative journey unless the operator performs the authorized guarded persistence step. Do not push/deploy code as part of routine itinerary use.

The browser retains its own confirmation/save flow. Stateless calls do not access its memory automatically; use explicit export/materialization and accurately explain that handoff. The current read-only report does not import browser data or provide a hidden save endpoint.

## Accumulate experience during use

Use existing facts/history, not another memory database. When the user reports an observation, outcome or evaluation, append a `fact` with optional `experience` metadata: source kind/time, event date (explicit unknown allowed), topics, conditions, unknowns and review needs. Link the actual plan/activity and relevant prior change commit IDs; do not invent the original intent or adjustment reason. Outcomes and personal evaluations need an explicit firsthand report. A held ticket or planned stop proves neither entry nor completion. External guides stay `external_guide`, with uncertain/current-rule limits intact.

If an incomplete experience later gains an outcome, append a newer sourced correction using `supersedesFactId`; retain the original record. Do not silently rewrite source material or establish a permanent preference from a one-off holiday queue, weather event or booking rule. Read `EXPERIENCE.md` for the complete contract.

For later planning, resolve relevant saved Library journeys, read their current versions and use `experiences` or explicit-state `experience-search`. It searches supplied data only; do not claim recall of trips or chats that were not retrieved. Check the result's source category, event date, conditions, unknowns and recheck labels before adapting it. Research the current weather, queues, rules and routes with already-authorized tools; only ask the user for an unresolved preference, ambiguity or missing firsthand outcome.

For a requested guide, select current experience records and write a general `draftLesson` through an authorized fact/correction if one is absent. Keep orders, contacts, exact private lodging/whereabouts and household details out of it. `guide-draft` omits private raw fields and withholds common sensitive patterns, but its free text still needs user privacy/accuracy review. Do not call a draft reviewed, published or shared without the corresponding user action; export alone grants no sharing permission.
