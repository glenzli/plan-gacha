# Itinerary core (guard revision 5)

The journey format stays schemaVersion 1. `content.itinerary` is optional with its own schemaVersion 1. Old journeys and historical receipts remain readable, with no automatic migration. New previews bind core revision 5. The stateless web/MCP snapshot tools remain the original four tools; richer itinerary operations are exported by the offline library and CLI. No second writer, hosted endpoint, new dependency, API call, key handling or OAuth is introduced.

## Import and persistence

AI converts user text into an explicit structured `import_itinerary` operation. The core validates it; it does not guess times, IDs, destinations or booking truth from prose. `anonymous-itinerary.json` contains a complete synthetic `{snapshot,operation}` example. Its dates and locations are fictional. Real journey debugging stays outside Git and the delivered packages.

1. Extract `snapshot` and initialize a new private journey with `init`. For an existing journey, read/verify its current state first; retain all existing plans, lodging and checklist data.
2. Extract `operation`, run `preview --revision N`, inspect the complete diff, analysis and reason codes.
3. Build a mutation with the same operation, revision and preview token plus explicit actor/reason/time/idempotency key. `apply` uses the existing local lock/CAS/fsync store; `stage` creates an unsaved candidate for the parent's guarded Library replacement.
4. Reopen `read`/`verify`, run `itinerary --input analysis.json`, then `undo` the latest commit if needed. Analysis input is `{asOf:"2030-05-11T12:00:00+08:00",dateId?:"2030-05-12"}`. No ambient clock is read.

Import normally uses new caller-supplied plan IDs, preserving the existing candidate catalog. Optional `adoptExistingPlanIds:[planId]` attaches typed data to already active plans only when ordered stable IDs, plan name and all projected fields are preserved exactly. Existing booking/lodging/checklist fields remain byte-equivalent in the snapshot; new end times/duration/constraints remain explicitly supplied assumptions. A nonempty assigned day requires explicit `replaceAssignedDays:[date]`; booked/locked/completed/confirmed arrangements still block replacement. Import never overwrites an existing baseline or automatically migrates the parent's authoritative journey. Adoption refuses missing IDs or mismatched current fields. Prepare a separately reviewed conversion if exact adoption is impossible; no ID generation, history rewriting or reservation narrowing occurs automatically.

## Three views, stable identity

`baseline:{source,days}` is immutable after import. `current` holds dated ordered activities. `actual` is an append-only list of user-reported events, separate from plans and reservations. `registeredActivityIds` retains removed IDs so IDs cannot be reused. IDs and all dates/timestamps are caller supplied. Typed time zone is explicitly Asia/Shanghai, not machine-local time. Legacy `Asia/Tokyo` and other original zone/date/clock values can be preserved and indexed through `import_history` without conversion (see HISTORY-IMPORT.md in the portable package). A known non-Shanghai snapshot timezone refuses typed conversion; do not relabel it as Shanghai. Local times use HH:MM; overnight ends require `endDayOffset:1`. An ISO actual timestamp must map to its stated Shanghai date and cannot follow the report timestamp.

Activities have `{id,kind,title,timing,source,location?,route?,note?,weatherSensitive?}`. Kinds: transfer, visit, meal, lodging, other. Transfers require an explicit driving/walking/transit route with from/to labels and optional stable endpoint activity IDs. Supplied durations, locations and times remain assumptions; they are not provider facts. Timing patches replace the timing object and retain omitted times as unknown. Location/route patches do not establish verified identity or fresh coordinates.

`edit_itinerary:{source,changes}` supports `insert` (date/index/activity), `remove` (activityId), `update` (activityId/patch), exact-permutation `reorder` (date/activityIds), `move` (activityId/date/index), and `add_day` with a new day/plan ID. A new day cannot silently displace an assigned day. Baseline and actual records survive edits. Current changes project into legacy snapshot plans/stops atomically so the shared snapshot evaluator sees the same current selection. Imported plans require `edit_itinerary`; legacy activity/assignment operations cannot fork the projection. Legacy booked links and plan/lodging locks remain protective. A finished activity cannot be rewritten. A started activity retains identity/date/order, while its future planned timing or note may change without modifying the separate actual report. Contradictory explicit finish times are refused; incomplete reports remain unknown. A past day's planned edit is refused; actual reports remain recordable.

`record_actual:{record}` accepts started/finished/skipped (with activity ID) or note/changed_plan. Exact `at` is optional; uncertain `bounds:{after?,before?}` retain exclusive local clock bounds. “After nine” stays an exclusive bound, not 09:00 or an invented precise departure. The reported lower-bound delay may be shown against the original start; it is not an arrival estimate. Congestion, a diversion or a ticket never creates an arrival/visit completion/check-in. Provider observations cannot establish user intent or actual progress.

## Constraints and protected commitments

`constraints` explicitly distinguish hard and soft. `start_at`, `end_before`, `end_by` require a target activity and clock. `max_driving_minutes` / `max_walking_meters` require a supplied numeric limit. `preference` is qualitative and soft: “less walking” never becomes an invented number. Add a later explicit constraint through `itinerary_constraint:{record}`. Constraint revision/removal is intentionally not automated by this prototype.

The core compares declared timetable values, reports unknown missing times, and exposes overlaps. `end_before:"17:00"` excludes 17:00; it is a user deadline, not evidence of sunset. Import can capture an already inconsistent source plan for review. Later edits cannot introduce/worsen hard clock violations or turn a known hard clock into unknown, and cannot introduce/worsen overlaps. Existing conflicts remain visible. Numeric limits use matching fresh live caller-supplied provider estimates when complete; absent coverage remains unknown. These checks do not solve roads/traffic or prove physical feasibility.

`commitments` and `itinerary_commitment:{record}` hold user-reported fixed/reserved arrangements, with explicit date and optional activity ID. Presence protects their current planned activity/day. A report is not an authenticated order. No operation executes or claims cancellation. This prototype intentionally requires separate user review before changing a protected arrangement; it does not release constraints/reservations implicitly. Old bookings with no confirmed activity links conservatively protect the whole day.

## Evidence and conditions

`itinerary-token --input {activityId}` returns a read-only content token. Attach a typed observation using `itinerary_evidence:{record}` with activity/date/token, source observation timestamp, explicit expiresAt, captureKind live/fixture, status estimate/unavailable/unknown and bounded detail. Route estimates need mode and a min/max duration range; weather needs risk and forecastDateId; place observations need matched/ambiguous/unknown identity. Optional route distance is meters. Provider evidence is supplied by the caller; provenance is not cryptographically authenticated by this engine. Existing walking-map tools remain available separately.

Binding covers the current dated activity and optional referenced endpoints. Edits invalidate old evidence conservatively, including timing edits; plan/date/location changes require a new observation. The latest observation wins: no fallback from a failure to an older success. Unknown/missing/ambiguous/wrong-date/future/expired/mismatched/fixture observations cannot become usable. A fresh route estimate can be compared with its declared slot or numeric limit. Weather clear is still only a forecast estimate. `feasibility` always remains `not_proven`. Fresh blocked weather shown for an edited day requires the existing explicit `acceptWeatherRisk`; stale weather becomes unknown.

Options are `{id,condition,proposal,dateIds,uncertainties,source}`: textual conditions for AI/user reasoning, not executable predicates. Decision points reference options with an optional exact deadline. An absent deadline remains unknown. Add later records using `itinerary_option` / `itinerary_decision_point`. `choose_option` records a user's intended choice and reason; it neither rewrites the schedule nor cancels an order. Separate activity edits must be previewed and saved. A hotel decision deadline can be reported without asserting free cancellation or verified fees. Closure rumors and unconfirmed forest reservations stay uncertainties; they do not delete activities.

Analysis returns open decision advisory events with exact deadline or unknown and `automaticAction:false`. External reminders already created by the parent are independent. The core does not poll providers, schedule notifications or cancel orders.

## Handoff limits

The engine/CLI can be called directly from AI; its input/output schemas are exported by the same library. The browser still owns confirmation of its own snapshot/local state. A stateless MCP call does not magically access browser data, and the richer journey itinerary is not yet a browser editor or new MCP protocol surface. Snapshot handoff requires an explicit export/materialization; the current portable CLI delivers a verified save/reopen/CAS/undo operator loop. Parent Library version is outer CAS, journey revision is inner CAS, schemaVersion is format. The tool never writes the parent's Library file itself.

## Decision matter lifecycle (guard revision 7)

Use `set_decision_status` with `decisionPointId`, `status:"completed"|"withdrawn"|"open"`, `confirmation:"explicit"`, `reason` and `source`. See [operator-flow.md](operator-flow.md) (portable `OPERATOR-FLOW.md`) for the full contract. This is distinct from choosing an option, actual activity progress or an order/refund action. Unknown evidence is retained as an uncertain fact/issue; provider evidence alone cannot establish completion.

The optional persisted `decisionPoints[].lifecycle` does not alter v5/v6 content or history on read. Analysis exposes `requiresAction`, inactive deadlines and active/inactive conditional options. Completion/withdrawal suppresses advisories, reopening restores them and invalidates older choices. Source times must advance; engine history retains the barrier after undo. Existing revision/token/idempotency and local/external CAS remain the only save path. Do not equate an old idempotent receipt with the current lifecycle state; read it again.

## Effective option eligibility (guard revision 8)

`analyseItinerary(i,input,{snapshot,memory})` and `renderItineraryReport` use the complete planning context to assess explicit `options[].requirements`. `set_option_requirements` attaches `{plans:[{planId,dateId}],reason,source}` without rewriting original prose. CLI/context/check supply this state automatically. `options` contains structurally eligible branches, `unassessedOptions` contains legacy or incomplete associations, and `inactiveOptions` preserves blocked/completed/past branches with reasons. Bare itinerary-only calls cannot establish snapshot/memory eligibility. See [operator-flow.md](operator-flow.md) for date scoping, stale bindings, choice invalidation and held-ticket uncertainty.
